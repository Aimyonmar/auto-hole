# 05 · 变现导向的价值模型与作业流程

> 本文回答一个很实际的问题：**同样跑一圈扫描，先提交哪个、哪些根本不值得提交。**
> 所有评分都是本地启发式，只用于排序与取舍；**不代表补天平台的实际定价，也不保证收益。**

---

## 1. 两条变现路径与工具能力映射

| 路径 | 平台规则要点 | 工具侧对应能力 |
|---|---|---|
| 公益SRC | 单点漏洞，KB 为主、部分现金；同一漏洞只投补天 | 域名级采集 → 指纹 → 定向 POC → 证据包 |
| 通用1.0 | 同一产品公网实例 ≥100，按危害/行业/时间跨度定价 | 产品型目标采集 → `inventory` 达标统计 → 产品分组扫描 → 证据包 |

工具不改变平台规则，只做三件事：**把资产规模说清楚、把高价值命中排前面、把提交材料准备好**。

---

## 2. 价值评分模型（`modules/recon/value.py`）

```
分值 = 危害基础分 + 漏洞类型加分 + 通用产品加分 + 资产规模加分
       - 证据缺失扣分 - 重复风险扣分
最终 = clamp(0, 100)
```

### 2.1 危害基础分

| 等级 | 分值 |
|---|---|
| critical | 55 |
| high | 40 |
| medium | 25 |
| low | 10 |
| info | 3 |
| unknown | 8 |

### 2.2 漏洞类型加分（只取最高一项，不叠加）

| 类型 | 加分 |
|---|---|
| 远程代码执行（RCE/命令执行） | +20 |
| 文件上传 | +18 |
| 未授权访问 / 越权 | +16 |
| SQL 注入 | +15 |
| 反序列化 | +15 |
| 任意文件读取 / 下载 / 目录遍历 | +12 |
| 默认口令 / 弱口令 | +12 |
| SSRF | +10 |
| 敏感信息泄露 | +8 |
| XSS | +3 |
| CSRF | +1 |

### 2.3 资产规模加分（通用1.0 的核心变量）

| 同产品存活实例（去重 host） | 加分 |
|---|---|
| < 10 | 0 |
| 10–99 | +4 |
| 100–999 | +8，且额外 +8（达到通用门槛）→ 共 16 |
| ≥1000 | 封顶 20 |

### 2.4 扣分项

| 情形 | 扣分 |
|---|---|
| 缺少 curl 复现命令 | -8 |
| 缺少回显/匹配证据（matcher/extracted/response 都没有） | -5 |
| 本库已有同模板“已提交”记录 | -12 |
| 本库已有同模板其它命中（更可能是补充资产） | -6 |
| 老 CVE（模板 CVE 年份 ≤ 当前年 - 3，公开 POC 多） | -6 |

### 2.5 等级与建议

| 分数 | 等级 | 建议 |
|---|---|---|
| ≥75 | S | 优先提交 |
| ≥60 | A | 优先提交 |
| ≥45 | B | 可提交（建议补强证据） |
| ≥40 | C | 价值偏低，作为补充资产 |
| <40 | D | 不建议提交（默认不生成证据包） |

> 示例：`critical + RCE + 120 台实例 + 通用产品` = 55 + 20 + 16 + 10 = 101 → 100 分（S）；
> 若是 2021 年的老 CVE，再 -6。

**为什么先算规模再算漏洞**：通用1.0 的定价由“同产品实例数 × 危害 × 行业 × 时间跨度”共同决定；
一个中危漏洞配上 300 台实例，往往比一个孤立的 critical 更值钱。

## 3. 通用1.0 作业流程（推荐顺序）

```powershell
# ① 建产品型目标：authorization 必填，hunter_query 写产品指纹语法
#    targets/myproduct.yaml:
#    name: "通用-致远OA"
#    authorization: "补天通用1.0 收录产品：致远OA（补天页面链接）"
#    hunter_query: 'web.body="seeyon"'

# ② 首跑：轻量档（并发 3 / 5 rps），只做采集+探测+指纹
main.py recon -t targets\myproduct.yaml --profile light

# ③ 盘点：看产品实例数够不够 100
main.py inventory --min-instances 100

# ④ 不够 100：把测绘平台导出的清单放到 workspace/import/<目标名>.txt
#    支持 host / host:port / URL / CSV（IP,端口,URL,标题）
main.py recon -t targets\myproduct.yaml --stage collect   # import 源会读入清单
main.py recon -t targets\myproduct.yaml --stage probe
main.py inventory

# ⑤ 达标后：按产品分组定向扫描（只跑该产品相关模板，省配额）
main.py recon -t targets\myproduct.yaml --stage scan

# ⑥ 生成证据包（价值分 ≥40 才生成），人工复核后提交
main.py recon -t targets\myproduct.yaml --stage evidence
```

提交时附：`workspace/recon/inventory.md`（产品实例数） + 单条证据包 + 时间戳截图。

## 4. 公益SRC 作业流程

```powershell
# ① 从补天厂商页确认域名范围，写进 targets/<vendor>.yaml（authorization 必填）
main.py recon -t targets\myvendor.yaml --profile light      # 首跑
main.py recon -t targets\myvendor.yaml --stage scan         # 显式扫描（standard 默认不扫）
main.py recon -t targets\myvendor.yaml --stage evidence     # 只给高价值命中出证据包
main.py scan -t targets\myvendor.yaml                       # 仍可走旧 CLI
```

## 5. 先打什么（按投入产出比）

1. **未授权访问**：一次 GET 就能证明，证据最干净，误报最低。
2. **文件上传 / 任意文件写入**：只验证接口存在与回显，不传利用文件（`strict_readonly` 已强制）。
3. **默认口令**：小字典、登录接口、命中即停（旧功能保留）。
4. **SQL 注入 / 反序列化 / RCE**：需要谨慎，只读验证；命中后立刻停手取证。
5. **信息泄露**：只有当泄露的是密钥/数据库配置/后台地址时才有价值，普通的版本号/目录列表优先级最低。

**不建议投入**：XSS（公益SRC 价值低且易误报）、CSRF、只暴露版本号的低危项、需要写文件的利用链。

## 6. 提交前检查清单（证据包内已内置）

- [ ] 人工复现一次，确认非误报
- [ ] 授权依据与资产范围正确
- [ ] 只读：未改数据、未上传文件、未拖库
- [ ] 证据含请求/响应/时间戳/目标 URL
- [ ] 未公开传播
- [ ] 与历史提交不重复（同模板多资产按“补充资产”提交，不拆洞刷分）
- [ ] 通用1.0：已附同产品实例数证明（≥100 台）

---

## 7. 常见“白干”情形（工具已尽量规避）

| 情形 | 工具侧处理 |
|---|---|
| 把 `type=http` 的命中过滤掉，跑完 0 结果 | 已修复（G1），并有回归测试 |
| 全模板扫描 14000 条模板，请求全花在无关目标上 | 按产品分组，只跑该产品模板目录；未识别产品默认不扫 |
| 低价值信息泄露刷屏 | 价值分 <40 不生成证据包，报告里排最后 |
| 同一 Nday 重复提交 | 同模板已在库 → -12 分并提示“补充资产” |
| 老 CVE 撞车 | 年份 ≤ 当前-3 → -6 分并注明 |
| 指纹误报导致打错 POC | `negative` 规则 + 置信度阈值 + 命中依据可回查 |

---

## 8. 风险与边界

- **不保证收益**：漏洞存量、竞争、厂商收录策略都影响实际结果；公益SRC 有相当比例只给 KB。
- **评分不是定价**：平台按危害/行业/时间跨度/资产数量综合定价，本模型只做相对排序。
- **规模不等于全部实例**：`inventory` 只统计本机已采集且存活的资产，不能替代平台测绘总量。
- **合规不可放松**：所有能力仍受“仅授权目标、只读取证、有界并发、全程留痕”约束；
  放宽速率必须填 `scan.authorization_ref`，绝对上限 64 并发 / 10 万日请求不可突破。
